# VPS Update Plan v0.1

Офлайн-планировщик поверх Audit из PR #17. Ветка зависит от этого PR; основное
меню, пункт 00 и целевые серверы не меняются.

Принимает чистый JSON Audit, без терминальных заголовков и строк проверки SHA256:

```bash
clear
python3 lib/vps_inventory.py audit |
    python3 lib/vps_update_plan.py --inventory - \
        --select tcp-c2 spamhaus-output auto-abuse-guard
```

Для уже сохранённого отчёта:

```bash
clear
python3 lib/vps_update_plan.py --inventory audit.json \
    --select tcp-c2 --format json
```

Выбор модулей обязателен. Планировщик сам не запускает Audit, не вызывает shell,
не делает запросов, не скачивает файлы, не пишет на диск и не запускает установщики.
Вывод — stdout. Источник и целевые хеши закреплены в update_catalog.json;
изменяемые URL и latest не используются. Ограничение входного JSON — 4 MiB.

| Статус | Значение |
| --- | --- |
| noop | Выбранный executable уже совпадает с целевым; это не health-check конфигурации |
| review_required | Хеш совпал с известной предыдущей версией; замена требует отдельной проверки |
| blocked | Неизвестный файл, служба/override, ОС или недоступная обязательная проверка |

Прежние хеши проверены по истории git. Одного сообщения known_content из Audit
недостаточно: планировщик самостоятельно сверяет digest с каталогом. Изменённый
файл нельзя объявить актуальным только сменой status в отчёте. Отсутствие файла
означает необходимость отдельного Install, не разрешение на Update.

Unknown, masked, failed и нестандартные drop-in не интерпретируются как безопасное
состояние. Неисправность несвязанного компонента не добавляет ему Install/Update.
Docker, контейнеры, Remnanode, DNS, SSH, маршруты, ядро и посторонние firewall-таблицы
не становятся шагами плана. Даже если модуль совпал с известной версией,
владение ресурсом не доказано.

`apply_available=false` и `update_gate=manual_review_required` неизменны. План не
содержит команд для применения и не является разрешением на замену. Проверка
свежести/привязки отчёта к хосту, полноценное версионирование, доказательство
владельца unit/config, backup, проверяемый rollback и применение — следующие этапы.
Текущее состояние служб и локальные настройки должны сохраняться при будущих
операциях; inactive/disabled не означает, что их надо включить.

Каталог обновлён относительно main после Inventory #17 и Spamhaus UDP #19.
Доступен явный выбор spamhaus-udp вместе с tcp-c2, spamhaus-output и
 auto-abuse-guard. UDP требует наблюдаемых служб восстановления/обновления
Spamhaus, но не добавляет обновление наблюдателя в выбранные операции.
Для firewall-модулей план требует известного сохранённого режима и указывает
preserve_saved_mode. Отсутствующий/неизвестный режим блокирует компонент;
сам режим не подтверждает live правила. Неизвестный SubState также блокирует
план. Ни один из этих статусов не разрешает применение изменений.
